## 一、简历怎么写

### 项目名称
**基于 RAG 的多模态电商智能导购 AI Agent（全栈个人项目）**

### 一句话简介
基于 LLM + RAG 的全栈电商导购系统，用户用自然语言描述需求，AI 实时流式完成"意图理解 → 商品检索 → 推荐理由生成"，并打通商品、购物车、订单的完整交易闭环。

### 简历 bullet（可直接用）

- 使用 **React 18 + TypeScript + Vite + Ant Design + Zustand** 构建前端，基于 **EventSource（SSE）** 实现 AI 回复的流式渲染与"思考中"状态实时推送；
- 使用 **Node.js + Fastify + Prisma + PostgreSQL** 搭建后端，设计 8 张表支撑商品、会话、消息、购物车、订单五个业务域，产出 20+ REST 接口；
- 设计 **LLM 意图识别链路**：将数据库真实分类注入 Prompt 约束模型输出，配合后端**分类名归一化**与**检索条件逐级放宽**策略，显著降低"AI 推荐零结果"率；
- 通过 **monorepo（pnpm workspace）+ 共享 types 包**保证前后端 SSE 事件协议强一致，协议变更编译期即可暴露；
- 搭建 **RAG 检索基础设施**：Qdrant 向量库 + OpenAI 兼容 Embedding 服务 + 商品文本向量化脚本，支持 90 件商品（10 分类）的语义索引构建；
- 编写脚本调用**火山方舟 Seedream 文生图模型**批量生成商品图，并产出完整的接口文档与数据库迁移体系。

### 技术栈关键词（过 ATS 筛选用）
`React` `TypeScript` `Node.js` `Fastify` `Prisma` `PostgreSQL` `Qdrant` `RAG` `LLM` `Prompt Engineering` `SSE` `Zustand` `Ant Design` `Docker` `Monorepo` `Zod`

> "这个项目是一个电商场景的智能导购 AI Agent。传统电商搜索要求用户自己把需求翻译成关键词和筛选条件，我做的系统允许用户直接用自然语言说'推荐一款 2000 元以内适合通勤的降噪耳机'，AI 会在几秒内流式返回：先展示思考过程，再给出商品卡片，最后生成推荐理由，并且可以直接加购下单。
>
> 技术上，前端是 React + Vite + Zustand，用 SSE 做流式对话；后端是 Node.js + Fastify + Prisma + PostgreSQL，按业务域分了商品、聊天、会话、购物车、订单五个模块；AI 层接入了 OpenAI 兼容的大模型做意图识别和文案生成，同时用 Qdrant + Embedding 搭了 RAG 检索底座。

## 三、项目讲解框架（STAR 法则）

### S — 背景（Situation）
- 电商选购决策成本高，关键词搜索无法表达"通勤用""送长辈"这类模糊需求；
- 通用大模型直接推荐商品会**幻觉**（编造不存在的商品/价格），不可信。

### T — 任务（Task）
- 构建一个以对话为入口的导购系统，要求：推荐必须基于真实商品库（RAG 思想）、响应要流式（体验）、能完成加购下单（闭环）、支持多轮对话与历史管理。

### A — 行动（Action，重点讲 4 件事）

**1. 设计 SSE 流式对话编排**
- 后端用 async generator（`streamChat`）把"保存消息 → 意图识别 → 检索 → 生成文案"拆成阶段，每个阶段 yield 一个事件（thinking / text / product），Fastify 原生流写入；
- 前端封装 `useSSE` + `useChat` 两个 Hook：无会话时先建会话再发消息（乐观渲染用户消息），thinking 事件只更新占位气泡不进消息列表，断流兜底 error 消息。

**2. 解决 LLM 输出与业务数据对齐问题**
- 意图识别时把数据库真实分类列表注入 Prompt，强制模型只能选存在的分类；
- 后端再做一层分类名归一化（去"品/类/用品"后缀 + 双向包含匹配），"护肤品"→"护肤"、"蓝牙耳机"→"耳机"都能命中；
- 检索零结果时逐级放宽：先放关键词，再放分类，保证"宁可近似、不可为空"。

**3. 保证前后端协议强一致**
- pnpm monorepo，把 `ChatMessage / IntentResult / Product` 等类型抽到 `@eaa/types` 共享包，SSE 事件结构改一处两端编译报错，杜绝协议漂移；
- 后端入参全部用 zod 校验，环境变量也用 zod 做启动期校验（缺 LLM key 直接启动失败，fail-fast）。

**4. 性能与成本的细节权衡**
- 会话标题生成刻意放在 SSE 流结束后**异步串行**执行——避免与意图识别并发调用 LLM 触发服务商限流，也不阻塞首条回复；
- 意图识别失败时降级为整句 keyword 模糊搜索，LLM 抖动不影响主链路可用性。

### R — 结果（Result）
- 完整跑通"对话 → 推荐 → 详情 → 加购 → 下单"闭环，90 件商品（10 分类）种子库；
- 20+ REST 接口 + 完整 API 文档 + 数据库迁移体系，一键 `pnpm dev` 启动；
- RAG 底座就绪（Qdrant + Embedding + 向量化脚本），具备演进为语义检索和 Function Calling Agent 的条件。

## 四、高频技术问答（必背）

### Q1：为什么用 SSE 而不是 WebSocket？

1. **业务模型匹配**：聊天是"一问一答"的服务端单向推送，不需要双向长连接；
2. **实现成本低**：SSE 基于普通 HTTP，无需额外协议升级和心跳管理，浏览器 EventSource 原生支持、自动重连；
3. **基础设施友好**：过代理/网关/CDN 无障碍，天然兼容 HTTP 生态（鉴权头、日志、限流）；
4. WebSocket 适合真正双向高频场景（协同编辑、弹幕），用在这里是过度设计。

*追问：SSE 的局限？* 只支持文本、单向、浏览器单域名连接数有限制（HTTP/1.1 下 6 个）；如果需要语音流双向传输会切 WebSocket/WebRTC。

### Q2：RAG 是怎么落地的？检索为什么没用向量数据库？

诚实回答（面试官欣赏这个）：
- 当前是 **RAG 第一阶段**：底座已搭好——Qdrant 入 docker-compose、Embedding 服务封装（OpenAI 兼容接口）、`build-vector.ts` 把商品"名称+分类+描述+卖点"拼成文档向量化；
- 在线检索先用**结构化条件查询**跑通了主链路，因为 MVP 阶段商品仅 90 件、意图已被 LLM 结构化（分类/价格/关键词），SQL 查询准确率更高、延迟更低；
- 演进路径清晰：商品文本写入 Qdrant 后做**混合检索**——向量语义召回 TopK（解决"跑步穿的鞋"这类无关键词匹配的场景）+ 结构化过滤（价格/库存硬条件）+ LLM 重排。

*这体现了工程判断：不过早引入复杂度，按数据规模选方案。*

### Q3：怎么防止大模型幻觉（编造商品）？

三道防线：
1. **检索增强**：模型只能基于检索到的真实商品生成推荐理由，商品卡片由系统直接插入而非模型生成；
2. **输出约束**：意图识别用 JSON mode + 真实分类列表注入 Prompt，把开放生成变成受限选择；
3. **后端校验**：分类名归一化 + 检索兜底，模型输出异常时降级为关键词模糊搜索。

### Q4：意图识别具体怎么做的？Prompt 怎么设计？

- 让模型输出固定 JSON：`{category, scene, minPrice, maxPrice, brand, keyword}`，开 `response_format: json_object`；
- Prompt 里注入数据库真实分类列表，category 只能从中选择，否则 null；
- 要求 keyword 限制在 1-2 个词（用于 SQL contains 模糊匹配）；
- 返回后统一把显式 null 归一化为 undefined，避免污染 Prisma 查询条件；
- 整个调用包 try/catch，失败降级为 `{keyword: 原句}`。

### Q5：数据库怎么设计的？关键决策是什么？

8 张表四个域：用户域（users）、商品域（categories / products / product_specs）、对话域（conversations / messages）、交易域（cart_items / orders / order_items）。关键决策：

1. **order_items 做快照**（存 productName、price 冗余字段）：商品价格会变动，历史订单必须保留成交时的价格与名称；
2. **cart_items 上 (userId, productId) 唯一约束**：重复加购走数量累加而非插新行，并发下也安全（数据库层面防重）；
3. **messages 表有 messageType 枚举**（text/product/compare/cart/error/thinking）：一条消息可以是商品卡片，metadata JSON 字段存意图和推荐商品 ID，可回溯"AI 当时为什么推荐这个"；
4. **金额用 Decimal(10,2)**，序列化层统一转 number，避免浮点精度问题；
5. 外键级联策略：删会话级联删消息、删商品级联删规格，但订单不级联删（审计要求）。

### Q6：多轮对话的上下文怎么管理的？

- 消息全部持久化到 messages 表，按会话 ID + 时间正序查询回放；
- 会话列表按 updatedAt 倒序，首轮对话后 LLM 自动生成智能标题（10 字以内），且只在标题是默认值时生成，不覆盖用户手改的标题；
- AI 回复的 metadata 里记录了当轮的 intent 和推荐商品 ID，后续可基于此做"上一轮推荐的那几款再对比一下"这类指代消解（规划中）。

### Q7：项目中的并发/性能考虑？

1. 意图识别与标题生成**刻意不并发**：LLM 服务商有 RPM 限流，标题生成放流结束后异步执行；
2. 商品列表 `count` 和 `findMany` 用 `Promise.all` 并行；
3. 分类解析这种高频小查询可加缓存（当前每次查库，优化点）；
4. SSE 连接的生命周期管理：前端收到 `[DONE]` 主动 close，异常时 onerror 兜底，避免连接泄漏；
5. 商品图批量生成脚本用线程池控制并发（默认 4），失败重试、已存在跳过（幂等）。

### Q8：怎么做错误处理和接口规范？

- Fastify 全局 errorHandler，统一返回 `{error, message, code}`；
- zod 在路由层校验入参（schema 与 handler 分离），非法参数 400；
- SSE 流内异常走 `data: {type:"error"}` 事件下发，前端渲染为错误气泡而不是白屏；
- 前端 axios 拦截器统一处理网络错误。

### Q9：如果让你继续做，下一步做什么？（考察技术视野）

1. **Agent 化**：把 `search_products / get_product_detail / compare_products / add_to_cart / get_cart` 封装成 Function Calling 工具，让 LLM 自主决定"先搜→发现两款都不错→主动对比→询问是否加购"，替代现在的固定流水线；
2. **混合检索**：向量召回 + 结构化过滤 + 重排，支撑"送长辈的礼物"这类无语义关键词的查询；
3. **多模态**：ASR 语音输入、TTS 播报、Vision 拍照搜同款（环境变量和数据模型已预留）；
4. **工程化**：接 JWT 真实鉴权替换 mock-user、引入 Redis 缓存热点商品与分类、加集成测试与 CI、SSE 接入 nginx 时注意关闭 buffering。

### Q10：遇到过最难的问题是什么？（行为题，选这个讲）

**问题**：上线联调时发现 AI 经常回复"没找到相关商品"，但库里明明有货。

**排查**：打印意图识别结果发现，LLM 把"护肤品"作为 category 返回，而数据库分类叫"护肤"，等值匹配必然为空。同类问题还有"蓝牙耳机"vs"耳机"。

**解决（三层）**：
1. Prompt 层：把真实分类列表喂给模型，要求只能从列表中选——从源头减少不匹配；
2. 服务层：分类名归一化（去后缀 + 双向包含匹配）——模型不守规矩时兜底；
3. 策略层：检索零结果时逐级放宽条件——最后防线，保证体验不崩。

**收获**：LLM 输出本质是概率性的，和确定性系统对接时必须假设它会出错，每一层都要有兜底，这就是"AI 工程化"和普通调 API 的区别。

## 五、可能被深挖的扩展问题

| 问题 | 回答要点 |
|---|---|
| Qdrant 为什么选它？ | 轻量、Docker 一键起、REST/gRPC 双协议、过滤条件与向量检索原生结合（payload filter），适合中小规模；替代方案 Milvus（大规模）、pgvector（少一个组件，数据量小时更优，可作为演进选项） |
| Embedding 模型怎么选？ | 中文场景评估 MTEB 中文榜单；当前走 OpenAI 兼容接口可插拔，默认 text-embedding-3-small（1536 维，性价比）；维度越高存储/检索成本越大 |
| 流式输出能做到逐 token 吗？ | 可以，LLM 接口开 stream=true，后端把 delta 逐个写入 SSE；当前是按事件粒度流式，演进时只需改 generateRecommendation 一处 |
| 怎么做 LLM 调用的可观测性？ | 记录 prompt/响应/token 消耗/延迟；messages.metadata 已存 intent 可追溯；生产可接 LangSmith/Langfuse |
| 订单并发安全？ | MVP 单机 SQLite 思维→PostgreSQL 事务；下单应放事务里（创建订单+清购物车+扣库存），库存扣减用乐观锁（version 字段）或 `UPDATE ... WHERE stock >= n` 条件更新防超卖 |
| 前端状态为什么选 Zustand 不选 Redux？ | 轻量（<1KB）、无 boilerplate、Hook 风格；项目状态规模（会话消息 + 购物车）用不上 Redux 的严格范式；消息按 conversationId 存 Map，切换会话 O(1) |
| 如何压测 SSE 接口？ | 用 k6/wrk 自定义脚本维持长连接统计 TTFB 和总耗时；关注 LLM 延迟是瓶颈（秒级），服务端本身不是瓶颈 |
