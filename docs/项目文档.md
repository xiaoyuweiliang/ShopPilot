# 基于 RAG 的多模态电商智能导购 AI Agent — 项目文档

> 文档版本：v1.0 ｜ 更新日期：2026-10-05

## 一、项目目的

传统电商的"搜索 + 筛选"模式要求用户自己把模糊需求翻译成关键词和筛选条件，选购效率低、决策成本高。本项目的目标是构建一个**以对话为核心的智能导购系统**：

- 用户用**自然语言**（未来扩展到语音、图片）描述购物需求，例如"推荐一款 2000 元以内、适合通勤的降噪耳机"；
- AI Agent 自动**理解意图**（品类、预算、场景、品牌偏好），从真实商品库中**检索候选商品**；
- 通过 **RAG（检索增强生成）** 让大模型的推荐"有据可依"，杜绝凭空编造商品；
- 打通"**咨询 → 推荐 → 对比 → 加购 → 下单**"的完整购物闭环，并支持多轮对话与历史会话管理。

本质上，这是一个把 **LLM Agent + RAG 检索 + 电商业务系统**三者融合的实践项目，也是一个可扩展为语音导购、拍照搜同款等**多模态**能力的底座。

## 四、核心功能

### 1. AI 导购对话（核心）

- **流式输出**：基于 SSE（Server-Sent Events）逐事件推送，前端实时渲染"思考状态 → 文本回复 → 商品卡片"。
- **意图识别**：LLM 从用户话语中抽取结构化条件（分类、场景、价格区间、品牌、关键词），且分类值**从数据库真实分类列表中约束选择**，避免幻觉分类。
- **商品推荐**：按意图检索商品，取 Top 3 以商品卡片形式插入对话流，可点击查看详情/加购。
- **推荐理由生成**：LLM 结合意图与候选商品的价格、评分、特点生成简洁推荐文案。
- **多轮对话与历史管理**：会话列表、消息持久化、删除会话、重命名标题；首轮对话结束后 LLM 自动生成**智能会话标题**（如"购买智能手表"）。

### 2. 商品系统

- 商品列表：分页 + 分类/价格区间/关键词组合筛选。
- 商品详情：基础信息 + 规格参数（ProductSpec）。
- 智能搜索 `/api/products/search`：供 AI 导购调用，**条件过严无结果时逐级放宽**（先放关键词、再放分类），保证"尽量有货可推"。
- **分类名归一化**：LLM 说"护肤品""蓝牙耳机"也能命中数据库中的"护肤""耳机"分类。

### 3. 商品对比（Compare）

独立的对比页面，多商品并排对比参数与价格（前端路由 `/compare`）。

### 4. 购物车

增（重复加自动累加数量）、删、改数量、查列表；导航栏实时显示购物车角标数量。

### 5. 模拟订单

- **订单预览**：按当前购物车计算明细与总金额，不落库。
- **创建订单**：购物车一键转正式订单（状态 `pending`），创建成功后自动清空购物车。

### 6. 种子数据与商品图片

- `import-products.ts`：程序化生成 10 大分类（耳机、跑鞋、笔记本、背包、手机、智能手表、键盘、鼠标、显示器、护肤）× 9 款 = **90 件商品**，含品牌、价格、评分、库存、卖点、规格参数，幂等可重复执行。
- `generate-product-images.py`：读取 `output/imagegen/products.jsonl` 任务清单，调用火山方舟 Seedream 模型并发生成商品图，存入前端 `public/products/`。

## 五、核心业务流程

### 5.1 AI 导购对话全流程（SSE）

这是系统的主链路，对应 `chat.service.ts` 的 `streamChat` 生成器：

```
用户输入文本
   │
   ▼
[前端] useChat.sendMessage()
   │  ① 无会话时先 POST /api/conversations 创建会话，路由跳转 /chat/:id
   │  ② 本地立即追加用户消息（乐观 UI）
   │  ③ EventSource 连接 GET /api/chat?payload={conversationId, message}
   ▼
[后端] chat.controller → chatService.streamChat()
   │
   ├─ 1. 会话 getOrCreate，用户消息落库（messages 表）
   │
   ├─ 2. ──SSE──▶ {type:"thinking", content:"正在理解你的需求..."}
   │      LLM extractIntent()：抽取 {category, scene, minPrice, maxPrice, brand, keyword}
   │      （category 受数据库真实分类约束；失败时降级为整句 keyword）
   │
   ├─ 3. ──SSE──▶ {type:"thinking", content:"正在检索商品..."}
   │      productService.search(intent)：条件查询 + 逐级放宽兜底
   │
   ├─ 4. ──SSE──▶ {type:"text", content:"为你找到 N 款相关商品："}
   │      ──SSE──▶ {type:"product", content:商品名, metadata:{productId}} × Top3
   │
   ├─ 5. ──SSE──▶ {type:"thinking", content:"正在生成推荐理由..."}
   │      LLM generateRecommendation() → 推荐文案
   │      ──SSE──▶ {type:"text", content:推荐文案}
   │
   ├─ 6. AI 回复落库（metadata 记录 intent 与推荐商品 ID）
   │
   ├─ 7. 若会话标题仍是默认"新对话" → 异步调用 LLM 生成智能标题
   │      （刻意串行执行，避免与意图识别并发触发 LLM 限流）
   │
   └─ ──SSE──▶ data: [DONE]  → 前端关闭连接
```

**前端渲染策略**：`thinking` 事件只更新占位状态气泡（"正在理解你的需求…"），不进消息列表；正式事件到达时替换为真实内容。SSE 断开时兜底插入 error 消息"服务暂时开小差了，请稍后再试。"

### 5.2 购物闭环流程

```
AI 导购推荐 ──▶ 商品卡片 ──▶ 商品详情（/products/:id）
                                  │ 加入购物车
商品选品页（/products 筛选浏览）───┘
                                  ▼
                    购物车（/cart：改数量 / 删除）
                                  │ POST /api/orders/preview 预览金额
                                  ▼
                    POST /api/orders 创建订单（pending）
                                  │ 自动清空购物车
                                  ▼
                            订单列表/详情
```

### 5.3 RAG 检索链路（现状与规划）

当前实现为 **RAG 的第一阶段**：

| 阶段 | 内容 | 状态 |
|---|---|---|
| 向量索引 | `scripts/build-vector.ts` 把"名称+分类+描述+卖点"拼成文本，经 embedding 模型向量化（当前打印维度，写入 Qdrant 为 TODO） | 🟡 框架就绪 |
| 在线检索 | `rag.service.ts` 已封装"意图文本 → 向量"的入口 | 🟡 框架就绪 |
| 实际召回 | 走 PostgreSQL 结构化条件查询 + 放宽兜底 | ✅ 已实现 |
| 混合检索 | 向量语义召回 + 结构化过滤（价格/分类）+ LLM 重排 | ⬜ 规划中 |

## 七、后端模块与 API

后端按 `controller（路由+参数校验 zod）→ service（业务+Prisma）` 分层，统一错误格式 `{error, message, code}`。详细接口见 [docs/API.md](./API.md)，摘要如下：

| 模块 | 路由前缀 | 主要接口 |
|---|---|---|
| 商品 | `/api/products` | 列表/分类/详情/智能搜索 |
| 聊天 | `/api/chat` | `GET /` SSE 流式导购对话 |
| 会话 | `/api/conversations` | 列表/创建/消息/删除/智能标题/改标题 |
| 购物车 | `/api/cart` | 查询/添加/改数量/删除 |
| 订单 | `/api/orders` | 列表/详情/预览/创建 |
| 健康检查 | `/health` | — |

**AI 相关服务**：
- `llm.service.ts` — 意图抽取（JSON mode）、推荐理由、会话标题，三次 LLM 调用各司其职；
- `embedding.service.ts` — OpenAI 兼容 embeddings 接口，未配置时复用 LLM 的 key 和 baseURL；
- `rag.service.ts` — 语义检索入口（待接 Qdrant）。

**鉴权说明**：当前版本未接入登录，所有接口使用启动时自动创建的 `mock-user`；`JWT_SECRET` 仅为占位。

## 八、前端架构

- **路由**：`/` 首页（品牌介绍 + 快捷需求标签）、`/chat/:conversationId?` AI 导购、`/products` 选品、`/products/:id` 详情、`/compare` 对比、`/cart` 购物车。
- **状态管理**：Zustand 双 store——`chat`（会话列表 + 各会话消息 Map）、`cart`（购物车条目与总数角标）。
- **聊天编排**：`useChat` Hook 串联"建会话 → 乐观渲染 → SSE 订阅 → 消息追加 → 错误兜底"；`useSSE` 封装 EventSource，将 `data:` 行解析为 `ChatMessage`。
- **消息渲染**：按 `type` 分发组件——文本气泡、`ProductRecommendCard` 商品卡、`ThinkingBubble` 思考气泡；侧边 `ConversationList` 会话列表与 `RecommendRail` 推荐栏。
- **类型安全**：前后端通过 `@eaa/types` 共享 `ChatMessage / IntentResult / Product / Order / Cart` 等接口，单一事实来源。

## 十一、关键设计决策

1. **为什么用 SSE 而非 WebSocket**：聊天是"一问一答式"单向推送，SSE 基于 HTTP、实现轻、天然支持断线语义，EventSource 浏览器原生支持。
2. **为什么意图识别约束真实分类**：LLM 自由发挥的分类名（如"护肤品"）与库中分类（"护肤"）不匹配会导致检索为空；通过把真实分类列表注入 Prompt + 后端归一化双保险，显著提升召回率。
3. **为什么检索要做"逐级放宽"**：AI 导购场景中"无货可推"是最差体验，宁可放宽关键词/分类条件返回近似商品，也不让用户面对空结果。
4. **为什么标题生成放在流结束后异步执行**：避免与意图识别并发请求 LLM 触发服务商限流，同时不阻塞首条回复的返回速度。
5. **为什么 monorepo + 共享 types 包**：前后端消息结构（尤其 SSE 事件类型）必须严格一致，`@eaa/types` 保证改一处、两端同步编译报错，杜绝协议漂移。
